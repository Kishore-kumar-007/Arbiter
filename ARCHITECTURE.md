# Arbiter — Human-in-the-Loop Decision Intelligence

## 1. Recommended Tech Stack
**Optimize for: CORRECTNESS > ARCHITECTURAL CLARITY > DEMO FEATURES > EXTRA POLISH.**

Given the 24-hour constraint and the need for typed schemas, a deterministic simulation engine, and clean API integration:

*   **Backend**: **Python 3.11+** with **FastAPI**. Python is excellent for logic-heavy simulation engines and has top-tier LLM integration. FastAPI provides automatic OpenAPI documentation and uses Pydantic for robust typed schemas, ensuring the AI outputs conform to our expected data structures.
*   **Frontend**: **React (Vite)** with **TypeScript**. Ensures a type-safe client that consumes the backend APIs cleanly. Using **Vanilla CSS** for styling to maintain flexibility and clean modularity.
*   **AI Integration**: Direct API calls (e.g., OpenAI or Google GenAI) structured to return JSON.
*   **State Management / Persistence**: **In-memory data structures** (Singletons) for the hackathon MVP. We will avoid setting up a database to save time and focus on the vertical slice, but the state will be serializable for easy transition to a DB later.

## 3. Domain Models / Entities (Pydantic/TypeScript Schemas)
*   **Zone (Location)**: `id`, `name`, `type` (building, road, safe_zone), `capacity`, `current_population`, `status`.
*   **Resource**: `id`, `type` (medical, security, fire), `status` (available, dispatched), `current_zone_id`.
*   **Incident**: `id`, `type` (fire, medical, crowd_surge), `zone_id`, `severity`, `description`, `status`.
*   **Situation**: A snapshot containing lists of `zones`, `resources`, `incidents`, and `timestamp`.
*   **Action**: `type` (dispatch, evacuate, block_route), `target_id`, `resource_id`.
*   **Strategy**: `id`, `title`, `actions` (list of Action), `explanation`, `confidence`, *metrics populated by engine* (`estimated_response_time`, `projected_risk`, `resource_consumption`, `constraint_violations`).
*   **DecisionRecord**: `id`, `timestamp`, `initial_situation`, `selected_strategy`, `human_action` (APPROVE/MODIFY/REJECT), `modifications`, `resulting_state`.

## 4. API Contract (RESTful)
*   `GET /api/state` - Fetch the entire current situation (Zones, Incidents, Resources).
*   `POST /api/incidents` - Inject a new incident to change runtime conditions.
*   `POST /api/strategies/generate` - Trigger the AI to analyze the state and generate candidate strategies. Returns the strategies *after* they have been simulated and scored by the deterministic engine.
*   `POST /api/strategies/simulate` - Provide a modified strategy payload. The engine runs a counterfactual simulation and returns the projected consequences without updating the real state.
*   `POST /api/decisions` - Submit a final decision (Approve/Reject/Modify). Updates the real system state and logs to the audit trail.
*   `GET /api/audit-trail` - Fetch the history of human-in-the-loop decisions.

## 5. State Model
The state is a global, immutable-style snapshot. When an action is approved, a new state snapshot is generated by applying the transition logic.
```python
class AppState(BaseModel):
    zones: dict[str, Zone]
    resources: dict[str, Resource]
    incidents: dict[str, Incident]
    time: int
```

## 6. Simulation Model (Scenario Simulation Engine)
The simulation is a pure function: `simulate(state: AppState, actions: List[Action]) -> SimulationResult`.
It deterministically calculates:
1.  **Response Time**: Distance between resource and incident zones.
2.  **Population Flow**: If an evacuation action is taken, checks the exit capacities of the zone.
3.  **Constraint Checks**: E.g., "Ambulance cannot enter a blocked road."
The LLM does NOT calculate these. It only proposes the `actions`.

## 7. Decision Scoring Engine
Once the simulation returns projected states, the scoring engine assigns a numerical score to the strategy based on weighted factors:
*   `resolution_speed`: How fast incidents are mitigated.
*   `resource_efficiency`: Minimizing the number of dispatched units.
*   `risk_reduction`: Projected decrease in severity or casualties.
*   `constraint_penalty`: Massive negative score for violated constraints.

## 8. AI Layer Interface
1.  **Input**: The backend serializes the current `AppState` into a compact JSON/Text summary.
2.  **Prompting**: "Given this situation, propose 3 strategies. For each, provide a title, explanation, and an array of structured Actions."
3.  **Output**: The LLM returns structured JSON matching a predefined schema.
4.  **Handoff**: The AI service parses the JSON into `Strategy` objects. It then passes these raw strategies to the **Simulation Model** and **Scoring Engine** to calculate all numerical fields (risk, time, violations). The LLM's generated metrics (if any) are discarded or used only as a heuristic.
